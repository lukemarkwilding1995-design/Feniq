# Request-specific inventory and scope review — 22 September 2026

Branch: `feniq-phase1-platform`. No migration, no change to `main`, and no private technical source files in Git.

Each admin-only customer request now has a read-only inventory at `GET /api/privacy-requests/{id}/inventory`. It follows explicit customer → site → passport and customer → work-order → inspection links, then linked technical cases. It lists record identities and a checksum of current record details, retained outcome/lifecycle/case histories and photo metadata. No search by customer name is used to infer ownership. The page explains that legacy free-text records, external systems, private library material and media bytes need separate manual review; the inventory is not an exhaustive subject-data export.

While a request is Investigating or Awaiting Decision, an admin may attest to an external identity check, review of linked records, and a separate check for unlinked records. `POST /api/privacy-requests/{id}/scope-review` records all three confirmations, a note and the exact inventory checksum in the immutable event history, using an optimistic request version. Closing requires a scope review for that request version and the still-current inventory checksum. A new link or changed record detail invalidates the previous review; further status transitions also require a fresh review before closure. Reopening a closed request requires investigation and review again.

For an active Access request with a current scope review, `GET /api/privacy-requests/{id}/access-preview` supplies an admin-only, no-store internal JSON draft containing explicitly linked customer contact, site, passport, work-order, inspection, outcome revision, photo metadata and case/lifecycle records. The UI lets an admin inspect this draft, with its request version and inventory checksum. It has no send, download or disclosure action. It omits media bytes and unlinked material; free-text entries can mention third parties and must be checked manually. A fresh linked-record change blocks the draft until another review.

The inventory also lists company-local inspections whose free-text customer field exactly matches the customer's name after whitespace and case normalisation, if they lack an explicit link. These are **possible unlinked leads**, never asserted as the customer's records. They remain excluded from the Access draft. Their record details, outcome revisions and photo metadata participate in the scope checksum, so a new matching inspection or changed lead requires another manual review. Differently spelled records can still be missed, and a matching name can belong to someone else.

The UI shows the inventory, its limitations, the review form and historical decisions. It does not disclose, correct, erase or send customer data. A fictional Willow House request displays linked site, passport, work order, inspection and technical case records in the local demo. Automated tests cover access boundaries, incomplete attestations, checksum mismatch, stale versions, changed links, closure gate, retained history and access-draft gating/tenant separation. Production work remains: an organisation-specific process for verifying requesters and making decisions, a controlled fulfilment route, more complete data mapping, third-party redaction and PostgreSQL validation.
